# 03 - יסודות Java ו־FTC

## קריאת קובץ Java

`package` ממקם מחלקה במרחב שמות התואם לתיקייה שלה. `import` מאפשר להשתמש בשם המקוצר של טיפוס. שם מחלקה ציבורית חייב להתאים לשם הקובץ. בהעתקת דוגמה אל `opmodes`, שנו את החבילה ל־`org.firstinspires.ftc.teamcode.opmodes` ואת שמות המחלקה והקובץ יחד.

מחלקה מרכזת מצב והתנהגות. שדות שומרים מצב בין קריאות; משתנים מקומיים קיימים רק בתוך הבלוק שלהם. בנאי מאתחל אובייקט, למשל `new MotorSubsystem(hardwareMap, "exampleMotor", Direction.FORWARD)`. המילה `extends` מציינת ירושה: ה־OpMode שלכם יורש מ־RobotCommandOpMode, המשתמש במחזור החיים של CommandOpMode מ־SolversLib. הסימון `@Override` מבקש מהמהדר לבדוק שהחלפתם מתודה בירושה כראוי.

`@TeleOp(name = "My TeleOp", group = "Team")` רושם OpMode לשליטת נהג. `@Autonomous` רושם OpMode אוטונומי. `@Disabled` מונע מדוגמה להופיע ברשימת ה־OpMode הרגילים לבחירה; קומפילציה לבדה אינה מפעילה אותה. `@Configurable` חושף שדות נתמכים דרך Panels, ולא דרך מהדר Java.

`private` מסתיר פרטי מימוש. `public` חושף ממשק. `static` מציין מצב המשותף למחלקה, ולא ערך לכל אובייקט. PoseFactory מסוג `static final` הוא מפעל משותף שאינו ניתן לשינוי; שדה הספק ציבורי וסטטי הניתן להגדרה עשוי להישמר בין מופעי OpMode באותו תהליך. אין להניח שכל INIT מאפס ערכים סטטיים.

## מחזור החיים בפרויקט

| מתודה | מועד הרצה | עבודה אופיינית |
|---|---|---|
| `initialize()` | פעם אחת לאחר בחירת INIT | איפוס מתזמן, מיפוי חומרה, יצירת תתי־מערכות וקישור כפתורים |
| `initialize_loop()` | שוב ושוב בזמן ההמתנה ל־START | הצגת תצורה ומצב; הימנעות מהתחלת תנועה |
| `preRun()` | פעם אחת אחרי START ולפני הלולאות הפעילות | פעולות התחלה לפי הצורך |
| `run()` | שוב ושוב בזמן פעילות | `super.run()` ולאחריו טלמטריה |
| `end()` | בסוף מחזור החיים הפעיל | ביטול פקודות ושחרור מנגנונים |

RobotCommandOpMode יורש מנגנון הרצה המבוסס על LinearOpMode. דרסו את המתודות האלה במקום לכתוב לולאת `while (opModeIsActive())` נוספת בתוך `run()`. תמיד קראו ל־`super.run()` בעת דריסה; הוא שמריץ את מתזמן הפקודות. שמרו גם על `super.end()` כשמוסיפים ניקוי משלכם. מחלקת הבסיס מבטלת פקודות גם לפני איפוס המתזמן. יצירת רכיבי חומרה יכולה להיכשל לפני תחילת השגרה; השתמשו בשמות משמעותיים ובדקו שגיאות INIT במקום להתעלם מחריגות.

Example01 אינו קורא ל־hardwareMap. מונה הלולאות שלו הוא מצב תוכנה מקומי, ואינו מספר השניות שחלפו: קצב הלולאה משתנה. השתמשו בטיימר למדידת משך וב־`WaitCommand` להשהיות ברצפי פקודות.

## למבדות, הפניות למתודות וספקי ערכים

למבדה היא התנהגות שמועברת כערך:

<div dir="ltr">

```text
() -> gamepad1.left_bumper ? 0.2 : 0.4
```

</div>

זהו `DoubleSupplier`: בקריאה אליו הוא קורא את מצב ה־bumper הנוכחי ומחזיר מספר. `BooleanSupplier` מחזיר ערך בוליאני. `motor::stop` הוא הפניה למתודה השקולה ל־`() -> motor.stop()`. ממשק מתאר פעולות שאובייקט תומך בהן; ספק הוא ממשק קטן עם מתודה אחת הדומה ל־getter.

ההבדל חשוב ביצירת פקודות. `double power = REQUESTED;` שומר מספר כעת. `() -> REQUESTED` קורא מאוחר יותר, אך רק כשהפקודה המקבלת מפעילה אותו. MotorSubsystem קורא לספק בכל מחזור ביצוע; ServoSubsystem קורא לספק המיקום פעם אחת באתחול הפקודה המיידית. ספק כשלעצמו אינו רץ אוטומטית בכל לולאה.

## חומרה, קלט וטלמטריה

`hardwareMap.get(DcMotorEx.class, "exampleMotor")` מבקש התקן מוגדר לפי טיפוס ושם מדויק. הוא אינו יוצר חומרה מדומה. שם או טיפוס חסרים גורמים לחריגה באתחול. ה־SDK מעדכן את מצב הבקר; דחיפת סטיק למעלה נותנת Y שלילי וימינה נותנת X חיובי. GamepadEx עוטף קלט לצורך קישור כפתורים. תוכנית ההתחלה הופכת את סימני הצירים כדי לבקש תנועה קדימה, שמאלה וסיבוב נגד כיוון השעון.

`telemetry.addData("label", value)` מוסיף ערך לתור; `telemetry.update()` שולח אותו. JoinedTelemetry שולח נתונים תואמים גם ל־Driver Station וגם ל־Panels. הציגו יחידות מועילות: `ticks/s`,‏ `in`,‏ `rad` או הספק מנורמל. מיקום סרוו מדווח הוא ערך הבקשה לבקר, ולא זווית פיזית שנמדדה.

תרגיל: העתיקו את Example01, הציגו את שני צירי הסטיק והוסיפו מונה שמשתנה בלחיצה על A באמצעות GamepadEx. חזו אם `if (gamepad1.a)` רגיל מגדיל פעם אחת או בכל לולאה. השתמשו ב[קישורי פקודות](04-commands.md) להתנהגות המופעלת ברגע הלחיצה.
